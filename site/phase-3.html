Step by step

  2. Diagnose the small-files trap: quantify median file size and file count growth from streaming writes. Confirm from the query profile whether the slow stage is scan/IO (too many small files, weak data skipping) vs shuffle/skew — do NOT fix what isn't slow.
  3. Compact with OPTIMIZE (bin-packing) on the worst table, then re-run DESCRIBE DETAIL and the benchmark query; record the new file count/size and runtime. Note the delta before adding clustering so you can attribute each gain.
  4. Add liquid clustering keyed to the QUERY PATTERN: ALTER TABLE ... CLUSTER BY (payer_id, hospital_ccn, billing_code) chosen from Maria's actual filters, then OPTIMIZE to realize the layout. Re-run the benchmark; record files pruned and bytes scanned vs baseline. Contrast with what naive partitioning by billing_code would have done (compute the resulting partition/file count on paper).

  6. Set retention + VACUUM: choose a defensible retention window (default 7 days; justify any change), run VACUUM in DRY RUN first, then for real, and note reclaimed bytes. Explain in the runbook how shortening retention would break time travel / concurrent readers.
  7. Rehearse recovery (build for failure): simulate a bad write (e.g. a MERGE that overwrites prices with nulls), detect it, then recover with RESTORE TABLE ... TO VERSION AS OF the last-good version; confirm row counts and a spot-checked price match pre-incident, and write an audit-log row (table, bad version, restored version, timestamp, why).
  8. Sanity-check idempotency isn't broken: re-run the streaming/incremental load once after tuning to confirm OPTIMIZE/clustering didn't change results, only layout.
  9. Write the Performance Notes section: a before/after table (files, bytes scanned, runtime, est. DBU) with a one-line headline LEADING WITH THE BUSINESS OUTCOME ('mart now lands ~4 min, comfortably before the 8am review; ~55% fewer bytes scanned'), then the technical changes underneath.

Step by step
  1. FREEZE & VALIDATE: cut a `release/v1.0.0` branch.   2. COLD-START DEPLOY: `databricks bundle deploy --target prod` into an empty prod-like workspace/schema so you prove nothing depends on hand-created state.   3. OBSERVE & PROVE QUALITY: watch the Lakeflow pipeline event log and expectation metrics; confirm the KPI mart lands inside the freshness SLA. Inject one deliberately malformed row and confirm it lands in quarantine WITH reason + timestamp and fires the alert — loud, not silent.
  4. PROVE IDEMPOTENCY: re-drop the exact same CMS file and re-run the Job 3× (aim for your standing 10× discipline). Assert zero net change in silver/golden via the watermarked, composite-key MERGE — no duplicate providers, quarantine counts stable.
  5. MEASURE FIRST, THEN TUNE: open the Spark UI / query profile for the slowest gold aggregation, identify the ONE bottleneck stage (skew, wide scan, or a big-vs-small join), apply exactly one fix (liquid clustering by query pattern / broadcast / repartition), and record before/after timing in Performance Notes led by the business outcome ("Maria's KPI mart now lands before 8am").

  7.
