Hands-on lab · ~3h

Stand up the course's foundational Git repository the way a real data team would: a Python virtual environment, one installed dependency pinned in requirements.txt, a tiny runnable script, a .gitignore that keeps secrets and the venv out of history, and a clear README. You practice the everyday DE workflow — feature branch, at least three small atomic commits, and a pull request you open, review, and merge — so the mechanics are muscle memory before any data is involved.

Step by step
  1. Create the repo skeleton locally: make the folder tree shown in the scaffold (src/, data/raw/, data/processed/, notes/, README.md, .gitignore, requirements.txt), then run `git init` and confirm `git status` shows the untracked files.
  2. Create and activate a virtual environment (`python -m venv .venv` then `source .venv/bin/activate`, or the Windows equivalent), install ONE package (e.g. `pip install requests`), and freeze it with `pip freeze > requirements.txt`. Verify `.venv/` is ignored by confirming it does NOT appear in `git status`.
  3. Write the small script `src/check_env.py` from the starter scaffold: complete the TODOs so it prints the Python version and confirms the installed package imports — this is your proof the environment is reproducible from requirements.txt alone.
  4. Make your FIRST commit on `main` containing only the baseline: .gitignore, README skeleton, and requirements.txt (do not commit .venv or data files). Confirm with `git log --oneline` that exactly one commit exists.
  5. Create and switch to a feature branch (`git switch -c feature/env-setup`), then build up the work in at least THREE atomic commits — e.g. (a) add `src/check_env.py`, (b) fill in the README run instructions, (c) add a `notes/decisions.md` entry. Each commit message states WHAT changed and WHY in the imperative mood.
  6. Push the branch to GitHub (`git push -u origin feature/env-setup`) and open a Pull Request whose description explains what the repo is for and lists the acceptance items as a checklist a reviewer can tick off.
  7. Self-review the PR diff in the GitHub UI as if you were a teammate: confirm no secrets, no .venv, and no large data files leaked into the diff; leave at least one review comment on your own PR, then merge it (squash or merge-commit, chosen deliberately) and delete the branch.
  8. Prove idempotency of your setup: on a clean checkout (or after `git switch main && git pull`), recreate the venv from scratch and run `pip install -r requirements.txt` followed by `python src/check_env.py` — it must succeed with no manual fixes. Record this in `notes/decisions.md`.
  9. Write a 4-6 line `notes/decisions.md` reflection: which files you deliberately kept OUT of Git and why, why you chose squash vs merge-commit, and what a teammate would need to reproduce your environment.

Why this matters NYC agencies dispatch crews (potholes, downed trees, heat/hot-water complaints) off dashboards fed by 311. When a complaint type is quietly renamed or a request lands with a null borough/lat-long, those rows drop out of the filtered view and the crew never gets routed — the outage is invisible because the dashboard still renders. Step by step

Fetch a snapshot: download the all_day CSV once to a local file (e.g. `curl -sL https://earthquake.usgs.gov/earthquakes/feed/v1.0/summary/all_day.csv -o all_day.csv`) so you develop against a stable copy, then open it and note the columns (time, latitude, longitude, depth, mag, place, ...) and confirm some `mag` fields are blank.

  3. Write parse_row(row): given a csv.DictReader row, return a clean dict with a float magnitude and a safe place string — but when `mag` is blank or non-numeric, do NOT default it to 0.0; instead flag the row as unparseable and return it (or None) so the caller can quarantine it. Handle malformed/missing place with a fallback like 'unknown location'.
  4. Quarantine bad records: collect every row that fails magnitude parsing into a rejected list with the reason (e.g. 'blank mag', 'non-numeric mag') and the event id, and write them to rejected.csv with a reason column — never let a bad row silently vanish or crash the loop.

Print a readable report: total rows read, count above threshold, counts per severity, the strongest event, and how many rows were rejected and why.

Why this matters NYC's restaurant-inspection feed repeats a venue's name, address, borough, and cuisine on every single inspection and violation row — so when a restaurant changes its name or moves, you either update dozens of rows correctly or silently corrupt your data, and a brand-new venue with no inspection yet can't even be recorded. Those are the exact update, delete, and insert anomalies that normalization exists to kill, and getting them wrong is how a public health dashboard shows a shuttered address as "grade pending."
