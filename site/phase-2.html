Concept lessons · ~7h
  • Lesson 8.1 — Why dimensional modeling exists (1.5h): the analytics failure mode of the 'one big table.' Recognition-before-evaluation framing: a hiring manager reads a README that says 'monthly cost report was wrong because the same hospital appeared 3 ways' and instantly recognizes the problem. Facts = the measurable business events (a charge, a price); dimensions = the who/what/where/how context you filter and group by. Contrast with W13's 3NF source shape: sources normalize to avoid update anomalies; analytics denormalizes into conformed dimensions to make questions cheap and answers auditable. Deliberately DEFER grain and the bus matrix to W15 — this week only establishes the fact/dimension split.
  • Lesson 8.2 — Anatomy of a fact table (2h): additive vs. semi-additive vs. non-additive measures (a charge amount is additive; a list price is non-additive/you cannot sum it across procedures). Foreign keys to dimensions, degenerate dimensions (a claim/line id that lives on the fact with no dimension table), and why a fact row should represent one business event. Worked on CMS MRF: the 'standard_charge|gross', 'standard_charge|negotiated_dollar', and 'standard_charge|min/max' columns are candidate measures; code|1|type, payer_name and plan_name point at dimensions.
  • Lesson 8.3 — Anatomy of a dimension: surrogate vs. natural keys (2h): why analytics uses an integer/hash surrogate key instead of the NPI or hospital EIN directly (stability across source drift, room for SCD2 history later, protection when a natural key is dirty or duplicated). Candidate business keys in the worked data: NPI (provider), CMS Certification Number / EIN (facility), CPT/HCPCS/DRG code (procedure), payer_name+plan_name (payer). Flag that provider identity is dirty (name/address variants, duplicates) — this foreshadows the MDM closer but is NOT solved this week.
  • Lesson 8.4 — The Project Charter as a data product spec (1.5h): translating Maria's pain into a written problem statement, a persona sketch, and 4+ KPIs with explicit formulas and measurement grain. Documentation-as-interview-prep: each KPI is a sentence you can defend in a screen. Introduce the four project KPIs (pricing-completeness pass rate, duplicate providers collapsed, records quarantined with reason, data-freshness SLA) as the charter's north star, and map each KPI to the fact/dimensions it will need.

Step by step

  2. Load silver_pricing_lines from W14 and compose a single grain_key by hashing the GRAIN_KEYS columns with sha2(concat_ws('||', ...), 256), coalescing nulls to a sentinel so a missing payer doesn't silently collide

It MUST contain at least one null price, one '$1,234.00'-formatted string price, one late-arriving record (older ingest date than its key already has), and one duplicate provider spelled/addressed two ways for the MDM test.
  2. Refactor for testability: pull your silver logic (price parsing, NPI normalization, address standardization, quarantine-reason tagging) out of notebook cells into pure importable functions in a transforms.py module — functions that take/return values or small DataFrames with no hidden I/O.
  3. Write ≥3 UNIT tests (@pytest.mark.parametrize): '$1,234.00' → 1234.00, ''/null price → quarantine reason 'MISSING_PRICE', and NPI ' 1234567890 ' → '1234567890'. These run in milliseconds with no Spark table.
  4. Write ≥2 INTEGRATION tests on the fixture (bronze→silver): assert bad rows land in the rejected table with reason + timestamp (and are absent from silver), and assert that re-ingesting an updated provider closes the prior SCD2 row (is_current=false, valid_to set) and opens exactly one new current row.

  6. Write ≥2 E2E tests: run ingest→bronze→silver→golden→gold on the fixture, assert the 4 KPIs are computed and sane; then run the ENTIRE pipeline a SECOND time and assert identical row counts and identical golden-record count — idempotency proven, not claimed.
